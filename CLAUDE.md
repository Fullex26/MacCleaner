# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MacCleaner (v2) is a macOS developer storage cleanup tool with two components:
1. **`cleaner.py`** — Python 3 CLI, single file, stdlib-only (the core engine for all scan/delete logic)
2. **`app/`** — SwiftUI menu bar + dashboard app (macOS 13+), a thin client over the CLI's JSON interface

## Commands

### CLI (subcommands are the primary interface)
```bash
python3 cleaner.py                    # No args = welcome screen
python3 cleaner.py scan               # What can be cleaned + sizes (--category, --min-size MB, --all, --json)
python3 cleaner.py clean              # Interactive cleanup (curses TUI checklist)
python3 cleaner.py clean --yes        # Auto-approve all safe targets (unattended/scheduled mode)
python3 cleaner.py clean --targets npm-cache,pip-cache --yes --json   # Agent mode: specific IDs
python3 cleaner.py clean --trash      # Move to ~/.Trash instead of deleting
python3 cleaner.py clean --dry-run --json   # Preview exact paths/sizes a clean would touch, zero side effects
python3 cleaner.py clean --yes --notify     # Post a macOS notification summarizing what was freed (used by the launchd agent)
python3 cleaner.py clean --min-free 45 --yes --json  # Clean safe targets, largest first, ONLY until 45 GiB free (agent fail-closed floors)
python3 cleaner.py projects           # Stale build artifacts (--roots, --min-age-days, --clean, --yes, --targets, --trash, --dry-run, --json)
python3 cleaner.py report -n 10       # Cleanup history from report.log (--json)
python3 cleaner.py report --stats     # Local-only usage stats aggregated from report.log (--json)
python3 cleaner.py doctor             # Environment health check (--json)
python3 cleaner.py categories         # List categories + targets (--json)
python3 cleaner.py config show|path|enable C|disable C|set KEY VALUE|sync on|off|status
python3 cleaner.py disk-check         # Cheap low-disk warning check, for launchd (--json); always exits 0
python3 cleaner.py storage-insights   # Read-only: largest items in Documents/Downloads/Desktop/~Library/Applications (--json)
python3 cleaner.py storage-map [PATH] # Read-only whole-disk browser, works outside $HOME (--min-size MB, --depth 1-3, --json)
python3 cleaner.py schedule status|weekly|monthly|off|run  # Manage/kickstart the launchd schedule (--json); status/off always exit 0
python3 cleaner.py install-deps       # Install 'rich' for pretty output
```

Every data command supports `--json`. JSON goes to **stdout**, human messages to **stderr**. Exit codes: 0 success, 1 runtime error, 2 usage error. `AGENTS.md` documents the machine contract.

**Legacy v1 spellings still work** via `translate_legacy()` pre-parse translation: `--preview`, `--clean [--yes]`, `--report`, bare `--json` (maps to `scan --json` — the old menu bar app contract), `--category`, `--config-show/--config-enable/--config-disable`, `--install-deps`; also aliases `preview`→`scan`, `history`→`report`. Existing cron jobs, shell aliases, and the v1 app keep working — don't break these.

Categories (23): `xcode`, `docker`, `node`, `python`, `caches`, `logs`, `homebrew`, `go`, `rust`, `ruby`, `cocoapods`, `gradle`, `maven`, `ai`, `ide`, `browsers`, `system`, `flutter`, `php`, `vms`, `tmp`, `simulators`, `leftovers`

### Install & Schedule
```bash
bash install.sh                        # Copies to ~/mac-cleaner/, adds aliases, installs the app
~/mac-cleaner/scheduler.sh weekly|monthly|remove|status
```

`scheduler.sh` is now a thin wrapper (`weekly|monthly` → `schedule <kind>`, `remove` → `schedule off`, `status` → `schedule status`, each via `exec` so exit codes pass through) over the `schedule` subcommand in `cleaner.py`, which is the actual scheduling logic and the only thing the app's Settings calls. `schedule weekly|monthly` installs two launchd agents (`com.fullex.maccleaner.clean` — `StartCalendarInterval`, runs `clean --yes --notify`; `com.fullex.maccleaner.diskwatch` — `StartInterval` 3600s, runs `disk-check`), replacing the old cron-based scheduling; both agents get an explicit `EnvironmentVariables.PATH` (Homebrew + standard dirs — the same list `CleanerBridge.runEngine` uses) so cmd-based targets don't silently no-op under launchd's minimal default PATH. launchd catches up on a missed calendar run after sleep/wake, unlike cron. `schedule status` calls `launchctl list <label>` per agent, so it distinguishes "loaded", "plist present but not loaded", and "not installed" instead of trusting a plist's mere existence, and always exits 0. **`_launchd_is_loaded()` is tri-state since 2.14.1** (`True`/`False`/`None`): only `launchctl`'s documented no-such-service answer (exit `113`, or a `Could not find service` message) is proof of not-loaded; every other failure — no `launchctl` on `PATH`, no Aqua/GUI session (ssh, sandbox, another launchd job), timeout — is `None`, "could not ask". Treating those as `False` made `doctor` report a healthy weekly schedule as broken and send the user to reinstall it. The JSON exposes this additively as `load_state` while `loaded` stays a plain bool, because `CleanerBridge.AgentStatus` decodes it as non-optional `Bool`; `schedule off` unloads both agents and also always exits 0, even when nothing was installed. `schedule weekly|monthly` exits 1 if either agent failed to load with launchctl. An existing cron line referencing `mac-cleaner/cleaner.py` (not an unanchored `cleaner.py` match, which could catch an unrelated user script) is stripped the first time `weekly`/`monthly` runs; the cadence actually installed is always the one you invoked, never the old cron line's own cadence, so migrating installs exactly once. `--json` on any `schedule` action returns `{"version", "schedule", "agents", "legacy_cron"}` plus `"migrated_cron"` (installs) or `"removed"` (off). `doctor`'s Schedule check and `schedule status` both derive from the same `_schedule_state()` helper, so both honor `MACCLEANER_LAUNCH_AGENTS_DIR` (default `~/Library/LaunchAgents`) and make the same `launchctl list` distinction; `doctor` also flags a leftover legacy cron entry.

After install, zsh aliases: `maccleaner`, `mclean`, `mpreview`, `mreport`.

### App Build
```bash
bash app/build.sh              # swiftc → build/MacCleaner.app (universal arm64+x86_64 when possible, ad-hoc signed)
bash app/build.sh --install    # …then copy to ~/Applications/
```
No Xcode project needed. The build bundles `cleaner.py` into `Contents/Resources/` as a fallback engine. `app/build.sh` itself always ad-hoc signs (`codesign --force --sign -`) — that's what every local/dev build gets. Real Developer ID signing + notarization happens only in CI, only on a tag push, and only when the signing secrets are configured (see `## Distribution` below); it never changes what `app/build.sh` does locally.

## Architecture

### Python ↔ Swift Bridge (the JSON contract)
The Swift app has **no cleaning logic**. `CleanerBridge.swift` runs `cleaner.py` via `Process` and decodes JSON from stdout into `Codable` models (`ScanReport`, `CleanResult`, `ProjectsReport`, `HistoryReport`, `CategoriesReport`).

**Superset rule**: additive JSON changes (new keys) are fine — already-installed apps keep decoding. Removing or renaming keys breaks the app models in `app/Sources/CleanerBridge.swift` AND the documented contract in `AGENTS.md` — update both if you must.

Engine resolution order: `MACCLEANER_ENGINE` env override (dev) → `~/mac-cleaner/cleaner.py` → bundled `Contents/Resources/cleaner.py`.

### App structure (`app/Sources/`)
Redesigned in v2.6 ("Glass & Sparkle"): sidebar navigation replaces the old tab bar, and the menu bar dropdown is a rich glass popover instead of plain text.

Eagerly touches `UpdaterManager.shared` at launch so Sparkle's daily background check starts even for menu-bar-only users who never open Settings.
- `DesignSystem.swift` — the one design system driving both light and dark mode: appearance-aware color helpers, the accent/chrome palette, a per-category color mapping, typography scale, motion constants, and shared surface components (`GradientBar`, `ReviewBadge`) so the sidebar, popover, and detail views stay visually consistent instead of drifting independently.
- `MenuBarPanel.swift` — the `MenuBarExtra` popover content: disk-usage ring + reclaimable-space hero number, top-3 categories, a one-click "Clean safe items" action with a self-expiring "freed" confirmation, an update-available banner (wired to `UpdaterManager`), and empty/footer states.
- `UpdaterManager.swift` — thin wrapper around Sparkle's `SPUStandardUpdaterController` (daily background check + manual "Check for Updates…" from Settings); also implements `SPUStandardUserDriverDelegate` for gentler scheduled-check reminders. Only meaningful in builds where `app/build.sh` actually embedded `Sparkle.framework` — see Distribution below.
- `DashboardView.swift` — grouped targets with checkboxes, in-app clean via `clean --targets … --yes --json`; also hosts `DiskTrendView.swift`, a Swift Charts free-space-over-time chart built from `report --json`'s `disk_history.snapshots`, with the low-disk threshold drawn as a dashed rule line and explanatory text when fewer than 2 points exist
- `StorageView.swift` — the Storage sidebar section (new in 2.11.0): a drill-down browser over `storage-map --json` with a breadcrumb trail, jump-to shortcuts (`/`, `/Applications`, `/Library`, `~/Library`, `~/Documents`), per-row proportional bars, Reveal in Finder, and **Move to Trash** — `FileManager.trashItem`, deliberately *not* the engine's delete path, since anything reachable here may be irreplaceable personal work and macOS's own permissions should decide what's off limits

A section's *minimum* height must stay under the window's 480 pt `minHeight`, or AppKit centres the overflow and pushes the top of both split-view columns off-screen — the Storage-tab bug that survived two fixes (2.13.0, 2.14.2) at 1513 pt. A new sidebar section must be added to the probe's list.

### Python cleaner.py internals
- `get_targets(config, all_categories=False)` — 94 static targets across 19 of the 23 categories, 72 safe and 22 review-level (verify with `python3 -c "import cleaner; t=[x for x in cleaner.get_targets(cleaner.load_config()) if x['category'] != 'logs']; print(len(t), sum(1 for x in t if x['safe']))"` — the `logs` filter is load-bearing: those targets are generated here too but are machine-dependent, one per oversized `~/Library/Logs` folder, so an unfiltered count prints a different number on every machine). 2.8.0 added three: `xcodebuildmcp-workspaces` (`xcode`, safe), `chrome-optimization-hint-cache` (`caches`, safe), and `chrome-optimization-model-store` (`caches`, **`safe=False` / review-only** — Chrome indexes those models in `Local State`, which this tool doesn't touch, so recovery is unverified and `--yes` must never take it). Each has a **stable kebab-case `id`** (e.g. `xcode-derived-data`, `npm-cache`), `label`, `description`, `safe` bool, and either a `path` (glob patterns with `*` supported), a `paths=[...]` list (2.10.0; several explicit sibling paths, for when the shared parent holds live state that must not be swept — `_target_paths` already understood this form, `add()` now passes it through, and `skip_paths` filters per entry so a skip retires one path rather than the whole target), a `cmd` (docker prune, brew cleanup, …), or `empty_only=True` (delete contents, keep dir — used for `~/Library/Caches` and `~/.Trash`). 2.10.0 added ten more (83 → 93), each verified to exist with real size on a working developer Mac before being added rather than guessed from vendor docs: `chrome-http-cache`, `spotify-browser-cache`, `clang-module-cache`, `electron-updater-pending` (`caches`), `typescript-cache` (`node`), `rustup-downloads` (`rust`), `ollama-updates`, `codex-sparkle-updates` (`ai`) — all safe — plus `codex-runtimes` and `antigravity-browser-profile` (`ai`, both **review-only**: a running Codex session may be executing out of the runtime dir, and the Antigravity profile holds live session state, not just cache). `electron-updater-pending` is the only glob among them (`~/Library/Caches/*electron-updater/pending`), deliberately scoped to the `pending` subdirectory so it takes staged installers without touching an updater's own bookkeeping; it matches only apps whose updater dir ends in that literal string, so Squirrel/ToDesktop apps are out of scope.

**`spotify-browser-cache` is the cautionary one, and the reason `add()` gained a `paths=[...]` multi-path form.** Its obvious path, `~/Library/Caches/com.spotify.client`, looks like a cache root but is actually the desktop app's embedded-Chromium profile — `Default/Login Data`, `Default/Cookies`, `Browser/Cookies`, `Local State`, and the `WidevineCdm` DRM module all live there beside the real caches. A `safe=True` target pointed at that root would let an unattended `clean --yes` silently destroy live session state. The target instead names the two regenerable subdirectories (`Browser/Cache`, `Data`) explicitly, recovering ~83% of the space with none of the risk. Two regression tests guard this class of mistake for *every* target, not just this one: `test_no_target_points_at_a_chromium_profile_root` fails if any `safe=True` target's resolved paths contain a `Login Data`/`Cookies`/`Local State` file, and `test_labels_are_unique` catches the indistinguishable-TUI-row bug that the original naming (`"Spotify cache"`, colliding with the existing `spotify-cache`) introduced. Note `chrome-http-cache`/`spotify-browser-cache` are **not** duplicates of the older `chrome-cache`/`spotify-cache` — those point at Application Support, these at `~/Library/Caches`; `test_no_new_target_duplicates_an_existing_path` pins that no two targets ever share a path. Three of the 23 categories, `tmp`, `simulators`, and `leftovers`, have zero static targets here — their targets are entirely dynamic (see `collect_targets` below).
- `_nested_build_dirs(parent, cutoff)` — new in 2.14.0; the one-level-deep half of the `tmp` scanner. AI-coding sessions leave a working directory holding logs, `.xcresult` bundles AND a build tree, so the directory itself is not junk but its build tree is — only the build tree is offered, never the parent. Content-classified like everything else here (the real case was a 4.1 GB tree named `derived`, and a folder merely *named* `DerivedData` with no build shape must not qualify). Bounded to exactly one level on purpose: an unbounded walk of every tmp tree would be slow and far likelier to surface something live. The same `tmp_min_age_days` cutoff applies — the real 4.1 GB case was zero days old, i.e. an active build, and the age gate is what protects it. `_classify_tmp_dir` also stopped requiring `info.plist` for the DerivedData signature (Xcode omits it under a custom `-derivedDataPath`); `Build/` + `Index.noindex/` plus one corroborating Xcode-only marker is the rule now.
- `collect_targets(config, all_categories=False, categories=None, target_ids=None)` — new in 2.5.0, extended in 2.6.0 and 2.7.0; what `scan`/`clean`/`clean --dry-run` actually call instead of `get_targets()` directly. Appends `tmp_to_targets(scan_tmp_artifacts(config))` when `tmp` is enabled, `scan_simulator_targets(config)` when `simulators` is enabled, and `app_leftovers_to_targets(scan_app_leftovers(config))` when `leftovers` is enabled, on top of the static list. `categories`/`target_ids` are v2.6 SELECTION HINTS from the CLI invocation (`--category`/`--targets`): when a hint proves a dynamic scanner's output can't possibly be selected, that scanner is skipped entirely — e.g. `clean --targets npm-cache` no longer pays a `simctl` call, a `/private/tmp` walk, or a `~/Library` leftover scan it was never going to use. **Hints only ever narrow, never widen** — `enabled_categories` still gates as before, and `categories=None, target_ids=None` (the default) behaves exactly like pre-2.6. `categories` (the subcommand, not this parameter) deliberately keeps calling `get_targets()` alone — the per-directory `tmp-<slug>`/`leftover-<id>` IDs are unstable across runs and the completions live-ID pipeline (`categories --json`) must never surface them. `scan_tmp_artifacts()` walks only the top level of the tmp root (`/private/tmp` by default, `MACCLEANER_TMP_ROOT` overridable), classifying a directory as junk purely by *content* (Xcode DerivedData shape, or a `.git` clone with a manifest + build-artifact dir) — never by name — and skipping symlinks, other-owner dirs, active `claude-*` session scratch dirs, and anything younger than `tmp_min_age_days`. `scan_simulator_targets()` shells out to `xcrun simctl list devices -j` / `runtime list -j` and produces up to two fixed, conditional IDs (`simulator-stale-devices`, `simulator-unused-runtimes`) whose `cmd` strings are built only from simctl UDIDs/identifiers that pass a strict regex first. `scan_app_leftovers()` (2.7.0) does a top-level scan of five bundle-ID-keyed `~/Library` subdirectories (`Caches`, `Preferences`, `Saved Application State`, `HTTPStorages`, `WebKit`) for entries whose bundle ID has no match in `installed_bundle_ids()`; `_leftover_candidate()` centralizes each root's real-world shape (directory vs. file, and which suffix to strip — `.plist`, `.savedState`, `.binarycookies`) so a wrong-shaped entry is skipped rather than misclassified, and `skip_paths` is honored the same way `scan_tmp_artifacts` honors it. `installed_bundle_ids()` scans each app root's top-level `.app` bundles PLUS one level into any non-`.app` wrapper folder (bounded, no further recursion) — some vendors (Adobe et al.) ship that way. Since that directory walk is inherently bounded (3 roots, ≤2 levels deep) and real vendors install arbitrarily deeper (Adobe Creative Cloud, Brother printer utilities, Steam-bundled games, …), `scan_app_leftovers()` runs a second confirmation pass after the walk, `_mdfind_confirms_installed()`: one batched, case-insensitive `mdfind "kMDItemCFBundleIdentifier == '<id>'c" || ...` query for every remaining candidate at once (never one call per candidate), excluding any bundle ID Spotlight reports as belonging to a real `.app` anywhere on disk. Additive only — the directory walk is untouched and still runs first — and it degrades to a no-op (empty set) on any failure (mdfind missing, Spotlight disabled, timeout, non-zero exit). Known gap even after this pass: Spotlight's own application importer does not index a `.app` nested *inside another app's* `Contents/` folder (verified with Alfred 5's internal preferences helper), so that specific nesting pattern is unreachable by either signal. All three dynamic families are always `safe: False` (review-only). The home-only rule in `delete_target`/`_safe_to_delete` has exactly one carve-out, and it's `tmp`-only: a `tmp_scan`-marked target (set only by `tmp_to_targets`) may delete a path outside `$HOME` if — and only if — that path resolves to a direct child of the tmp scan root **or one level below it** (widened from one level to two in 2.14.1: 2.14.0 began offering the build tree *inside* a workspace so the sibling logs survive, and the direct-children-only rule refused every one of those targets at delete time — the feature could not reclaim a byte); three levels deep is still refused, the `tmp_scan` marker is still required, and no config key widens it. `leftovers` needs no carve-out — every root it scans is already strictly inside `$HOME`.
- `scan_storage_map(root=None, min_bytes=0)` / `_du_children()` / `_storage_category()` — new in 2.11.0; the **read-only whole-disk browser** behind `storage-map`. One level of children beneath `root` (default `$HOME`), largest first, and — unlike everything else in the engine — it reads **outside `$HOME`** (`/Applications`, `/Library`, `/`). It is not part of the target family: entries have no `id`/`safe`, are never passed to `delete_target()`, and there is no delete flag. Deletion for these paths exists only in the app, via `FileManager.trashItem` (recoverable), never the engine's hard-delete path. **`_du_children` must keep `du -xkd 1`'s `-x`**: without it `du` descends into mounted disk images and counts their contents on top of the image file, which made `/Library/Developer/CoreSimulator` measure 106 GB against a real 11 GB — pinned by `TestStorageMap.test_does_not_cross_mount_points`. Note the older `get_size()` (`du -sk`, no `-x`) has the same latent flaw, currently harmless only because every target path it measures is inside `$HOME` and free of mount points.
- `scan_storage_insights(config)` / `_bundle_size()` / `_disk_bytes()` — the read-only "largest items" scan behind `storage-insights`. Stat-only (`os.scandir`/`os.stat`, never opens contents, so it can never trigger an iCloud download of an evicted file) — and **`_bundle_size()` is deliberately a stat-walk rather than `du`/`get_size()`**, so that guarantee stays provable by mocking `builtins.open`. Deliberately outside the `get_targets()`/`collect_targets()` family: no `id`/`safe`/`category`, never passed to `delete_target()`. Three things changed in 2.13.0, all driven by a real machine where the old version could see almost none of the disk:
  - **Six roots, not three** (`~/Documents`, `~/Downloads`, `~/Desktop`, `~/Library`, `~/Applications`, `/Applications`). `~/Library` alone was 85 GB vs ~35 GB of Documents. The JSON now echoes `roots` and `min_bytes` so an empty result is distinguishable from an unscanned root.
  - **Bundle-aware** (`STORAGE_INSIGHTS_BUNDLE_SUFFIXES`): a `.app`/`.framework`/`.photoslibrary`/… is one entry carrying its whole size with `is_bundle: true`, never descended into. Load-bearing for `/Applications`, which holds **zero** loose files over the 100 MB floor and a dozen multi-GB bundles — without this it returns nothing at all.
  - **`_disk_bytes()` = `st_blocks * 512`, not `st_size`.** Apparent size lies for sparse files: `Docker.raw` reads 1.0 TB apparent against 9.97 GB allocated, which put a phantom terabyte atop a largest-items list on a 460 GB disk. Matches `du`/Finder, and is also correct for APFS-compressed files. `STORAGE_INSIGHTS_MAX_RESULTS` rose 50 → 100 to fit the wider roots.
- **Hang guards in `scan_storage_insights` (2.17.2).** Two engines were found wedged 20+ minutes in `getdirentries64` on an evicted iCloud Pages document under `~/Library/Mobile Documents` — stat on a dataless folder is fine, *listing* it blocks until iCloud downloads it, and the old "stat-only so never triggers a download" claim was only true for files. `_is_dataless(st)` checks `SF_DATALESS` on every directory's lstat before `os.scandir`, in the main walk and in `_bundle_size` (which now takes a `stats` dict); flagged folders are counted, never entered. A `time_budget_s` (default `STORAGE_INSIGHTS_TIME_BUDGET_S`=120) stops the walk *between* directories, and `CleanerBridge.runEngine` has a hard SIGKILL timeout (10 min default, 180 s for this call) plus a `scanStorageInsights()` re-entrancy guard (the Scan button chained a second walk onto a stuck one).

  **2.17.3: the dataless guard is necessary but NOT sufficient, and the between-directories budget could not save it.** A directory can block `readdir` forever without carrying `SF_DATALESS`: `~/Library/Containers/com.apple.dt.ExternalViewService/Data` on a real developer Mac is a plain user-owned directory (mode `0700`, `st_flags == 0`, not dataless, not iCloud — an Xcode app container) on which a bare `os.listdir()` never returns. A real scan sat in `os_scandir` on it for **12 minutes at 0% CPU** and the CLI, which has no SIGKILL backstop, hung indefinitely. Since a readdir already blocked in the kernel cannot be interrupted from Python, the budget must bound **the walk itself, not the gaps between its steps**: `_walk()` now runs in a **daemon** thread that the caller `join`s with `time_budget_s`, and a wedged thread is abandoned rather than waited on (daemon, so it can never keep the process alive; hits it already appended stay valid, since `list.append` is atomic under the GIL). Verified live on the machine that hung — 12+ minutes became a clean 120.2 s return with `truncated: true` and 47 real results. **Do not "fix" a future hang by adding another skip-this-kind-of-directory rule** — enumerating classes of blocking directory is a losing game, which is exactly what this case proved; the bound is the fix. `scan_storage_insights(config, stats=None, time_budget_s=None)` fills `stats` with `dataless_dirs_skipped`/`truncated`/`elapsed_s` rather than changing its return type; `storage-insights --json` exposes the first two additively. Tests fake the flag with a `DirEntry` proxy since only the kernel can set it.
- `_trim_cron_log()` / `CRON_LOG_MAX_BYTES` / `CRON_LOG_KEEP_LINES` — 2.17.2; `run_disk_check` (the hourly launchd writer) trims `cron.log` to its last 400 lines past 512 KiB, **in place** — launchd holds `StandardOutPath` open with `O_APPEND`, so a rename-rotate would strand its descriptor on the old inode.
- `_installed_app_bundles()` / `_homebrew_cask_app()` — 2.17.2; `doctor`'s "Menu bar app" check now lists every copy (`~/Applications`, `$MACCLEANER_SYSTEM_APPLICATIONS_DIR`), fails with a remove-this-one remedy when there are two, and names the Homebrew-managed one by resolving the Caskroom's `<version>/MacCleaner.app` symlink (`MACCLEANER_CASKROOM_DIR` override; compare **resolved** paths — `/var` vs `/private/var` bit the first version). The engine/app version-skew check compares against the Homebrew copy when present, since Sparkle and `brew upgrade` both track that one and the other only drifts. `install.sh` has matching shell helpers, `maccleaner_cask_app` (skip the app step when Homebrew owns it) and `dedupe_maccleaner_shortcuts` (remove exact repeats of our own `~/.zshrc` function lines, first occurrence wins); `TestInstallScriptHelpers` slices each function out of the script with `sed` and runs it in a throwaway bash, so no real rc file is touched.
- `reclaimable_total(targets)` — new in 2.12.0; what both `scan` totals now use instead of `sum(t["size"])`. 27 targets nest inside `general-caches`, so the plain sum double-counted them (2.5 GB overstated on a real machine). A target whose every resolved path lies inside another target's path is skipped — nobody frees the same byte twice. Nesting is tested with a trailing-separator prefix check so `/x/Caches2` is not mistaken for a child of `/x/Caches`; `cmd` targets have no path and always count.
- `_docker_disk_image()` / `DOCKER_IMAGE_WARN_BYTES` / `DOCKER_RAW_PATHS` — new in 2.14.0; a fourth **advisory** `doctor` check. Sizes Docker Desktop's `Docker.raw` by `_disk_bytes()` (allocated blocks), because the file is sparse — 1.0 TB apparent vs ~10 GB real. Unlike the other advisories the space IS reclaimable, just not from outside: only Docker's own TRIM shrinks the host-side image, and only while Docker runs. Never a target; truncating/deleting the image destroys every container, image and volume.
- `_system_temp_usage()` / `SYSTEM_TEMP_WARN_BYTES` / `SYSTEM_TEMP_WARN_ENTRIES` — new in 2.12.0; a third **advisory** `doctor` check (alongside `Swap` and `Held-open files`) reporting macOS's per-user `$TMPDIR`. Flags at 5 GiB **or** 2000 entries — the entry count matters independently because size depends entirely on when you look (one machine: 16,289 entries / 3 GB, having been 20 GB hours earlier). Report-only, never a target, never affects top-level `ok`; `/tmp` is deliberately excluded since that is the cleanable `tmp` scanner's territory. **`run_doctor()` now returns `{"ok", "checks"}` rather than a bare bool** — `main()` still discards it, so `doctor` still always exits 0, but individual checks are now assertable without re-parsing printed JSON.
- `measure_targets(targets)` — parallel `du -sk` via `ThreadPoolExecutor`; cmd targets use `estimate_cmd` parsers
- `get_size(path)` — `du -skx`. The **`-x` is load-bearing** (added 2.12.0): without it `du` descends into any mounted volume beneath `path` and counts that image's contents on top of the image file itself, reporting the same bytes twice. That flaw made one directory measure 106 GB against a real 11 GB when checked by hand. No current target contains a mount point, but nothing verifies that when a target is added.
- `delete_target(t, mode)` — refuses anything outside `$HOME` (and `$HOME` itself / `/`), never follows symlinks (unlinks them); `mode="trash"` moves to `~/.Trash` instead (the `trash` target always hard-deletes)
- **`cmd_runner` targets** (issue #106) — a target may carry `cmd_runner` + `cmd_ids` instead of relying on its `cmd` string being shell-executed. `delete_target` dispatches on it and **never falls through to the shell for such a target, including for a `cmd_runner` it does not recognize** (that is an error, not a reason to guess): their `cmd` is a faithful *description* of the commands, what `--dry-run` prints, not a string vetted for `shell=True`. Both `simulators` targets use it. `simulator-unused-runtimes` previously built `"; ".join("xcrun simctl runtime delete %s 2>/dev/null" % i) + "; true"`, which destroyed three signals at once — stderr, the exit code, and therefore `delete_target`'s `status = "error" if err else "deleted"`. It reported `status: "deleted"` / `freed: 0` on a real machine while ~21.2 GB of runtime assets stayed on disk. `_simctl_delete_verified` runs one process per identifier (`_simctl_run_owned`: no shell, own process group, file-backed stderr, group killed on every exit path) and then **re-reads simctl's registry**: anything still registered is a failure whatever simctl's exit code claimed, and an *unanswerable* re-read is reported as unverified, never as success. Iterating in Python is what preserves the one property the `; `-join was chosen for — a bad identifier must not short-circuit the rest. `_simctl_registered_runtime_ids()`/`_simctl_registered_device_udids()` return `None` for "could not ask" and an **empty set** for "nothing registered": conflating them (`{}` is falsy) would turn deleting the last runtime, the one fully successful case, into a permanent "could not verify". Do **not** replace the hand-rolled "runtimes with no devices" selection with `simctl runtime delete --outdated/--unusable/--notUsedSinceDays`: those express a different and narrower notion (a current runtime with no devices is neither outdated nor unusable), and letting simctl pick the set means the engine can no longer enumerate, size or show the user what is about to go — which is the whole contract of a review-level target.
- **`freed_unknown`** — `_freed_unknown_field(t)` stamps `{"freed_unknown": True}` on every cmd-target item in `run_clean`/`run_clean_min_free`, emitted only when true (the `advisory` idiom). `freed` stays a plain int: `CleanItem.freed` is a non-optional `Int` in already-installed copies of the app, so making it `null` would break them. A cmd target's reclaim is genuinely unmeasurable — and for simctl the bytes may sit in SIP-protected `/System/Library/AssetsV2/com_apple_MobileAsset_*SimulatorRuntime/` bundles the engine can never see, so a verified *deregistration* is not proof that space came back.
- **`reclaim_unverified`** — `_reclaim_unverified_fields(t)` is the scan-side half of `freed_unknown`: `{"reclaim_unverified": True}` plus a human `reclaim_note`, emitted only when present (same additive idiom), and `reclaimable_total()` leaves such a target out of `total_reclaimable_bytes` while `size_bytes` stays exactly as measured. Only `simulator-unused-runtimes` carries it (issue #112). Its size is simctl's `sizeBytes`, and **simctl lists only currently-mounted runtime images**: on a real machine `runtime list` fell from 7 runtimes / 43.20 GiB to 2 / 11.1 GiB in ten minutes with nothing deleted and no reboot, so both the target's membership and its size move on their own — and #109's post-delete registry re-read can report a clean `deleted` purely because the image happens to be unmounted. Four recorded runs freed 0 bytes with 43.20 GiB of images still on disk after a reboot. **Do not "fix" this by deleting the target**: enumerating and sizing what is about to go is the whole contract of a review-level target, and the supported removal path (named in `description` and `reclaim_note`) is Xcode → Settings → Platforms, which drops registration and image together. `simulator-stale-devices` is deliberately **not** marked — device data under `~/Library/Developer/CoreSimulator/Devices` really is freed.
- `run_dry_run(targets, mode, json_mode)` — resolves exactly what a real `clean` would delete (concrete paths + sizes, or the command that would run) without deleting anything or writing to `report.log`/`snapshots.log`; used by `clean --dry-run` and `projects --dry-run`
- `scan_projects(config)` — walks `project_roots` to bounded depth for artifact dirs (`node_modules`, `.venv`, `target`, `build`, `Pods`, `.next`, …) requiring a sibling manifest (`package.json`, `Cargo.toml`, `pyproject.toml`, …) and min age (default 30 days); never descends into artifacts. When `project_git_check` is on (default), each hit's project dir is also checked with `git` for uncommitted/unpushed work (`_git_info`); dirty/unpushed projects are excluded from `projects --clean --yes` unless named via `--targets`. **Skips evicted iCloud directories (2.17.3)** — `_is_dataless(st)` is checked before descending, because this walk is recursive and `~/Documents` is a default project root that is iCloud-backed under "Desktop & Documents Folders" sync. Same hang 2.17.2 fixed in `scan_storage_insights`: `stat` reports the flag cheaply, but *listing* a dataless directory blocks in `getdirentries64` until iCloud materialises it, and unlike `storage-insights` this walk has no time budget to bail out of. The skip is also what keeps an evicted artifact dir out of the delete list — its real size and contents are unknown until it comes back down. Note `scan_app_leftovers` needs no such guard: it lists only each root's top level and never descends, and stat on the entries is safe
- `_notify(title, message)` — posts a macOS notification via `osascript`; never raises, warns on stderr and returns `False` on failure so a notification problem never fails a clean. Always shows a generic icon (`display notification` has no attribution option). Used by `clean --notify` (honours config `notifications`) and `run_disk_check` (when posting itself)
- `run_disk_check(config, json_mode, post=True)` — one `shutil.disk_usage` call, no measurement or snapshot; warns via `_notify` when free space is below `low_disk_threshold_gb` (default 10 GB, falls back with a stderr warning if malformed), throttled to once per 24h via `alerts.json`; **always exits 0**. `post=False` (CLI: `--no-post`, new in 2.9.1) skips the `_notify` call but still makes and persists the throttle decision, exposed as a new `should_notify` JSON field independent of `notified` — this is what the app uses to deliver a correctly-iconed in-process notification itself (`NotificationManager`) instead of the generic-icon osascript one, sharing the same `alerts.json` throttle as the standalone launchd `diskwatch` agent so the two never double-notify
- `run_doctor(config, json_mode=False)` — checks python, rich, config validity, install, schedule (launchd agents + legacy cron), schedule paths, app, engine/app version skew, tool availability, disk, plus (2.8.0) two **advisory, report-only** system-pressure checks: `Swap` (one `sysctl vm.swapusage`; flags at `SWAP_WARN_BYTES` = 8 GiB of **swapfiles on disk** — an absolute disk-consumed threshold, never a used/total ratio, which survives only as informational text in the status; no "restart to free it" advice, since macOS re-grows the files in minutes) and `Held-open files` (one `lsof -b -nPw +c 0 +L1`; conditional, appears only at ≥500 MB of deleted-but-still-open files, deduped by `(DEVICE, NODE)`). Both never delete, never become targets, and degrade to a quiet "could not determine"/omission on any failure. Its internal `check(name, status, ok=True, advisory=False)` emits `"advisory": true` **only when true** (so pre-2.8 entries stay byte-identical), and the aggregate is `all(c["ok"] for c in checks if not c.get("advisory"))` — **advisory checks never flip top-level `ok`**, which keeps `ok` meaning "a MacCleaner-owned problem with a remedy". `main()` still discards the return value: `doctor` always exits 0.
- `_stranded_simulator_assets()` / `_registered_simulator_runtimes()` / `_asset_build_and_version()` / `SIMULATOR_ASSET_PLATFORMS` — the `Stranded simulator runtimes` advisory. A simulator runtime MobileAsset under `/System/Library/AssetsV2/com_apple_MobileAsset_{iOS,watchOS,tvOS,xrOS}SimulatorRuntime/<sha>.asset` that no listed runtime is mounted out of becomes **invisible to every tool and removable by none**: simctl has lost the handle (no `--outdated`/`--unusable`/`--notUsedSinceDays` selector matches an image it no longer lists) and the directories carry SIP's `restricted` flag, so `rm -rf` fails even as root. ~21.2 GB unaccounted for this way on a real machine (issue #108). The advisory means "no mounted runtime accounts for these bytes" — **not** "a delete stranded them": issue #112 found no evidence that any `simctl runtime delete` on that machine ever deregistered anything, and simctl's own list shrank from 7 runtimes to 2 in ten minutes with nothing deleted. The asset's build comes from `Info.plist`'s **`MobileAssetProperties.Build`** (nested — a top-level `Build` is only a fallback, and `plutil -p | grep Build` cannot tell the two apart), cross-referenced against every `build` in `xcrun simctl runtime list -j` **plus** the `.asset` directory each listed runtime is mounted out of (`path`/`parentMountPath`/`runtimeBundlePath`) — the path is a second, independent signal so a build-string mismatch can never be reported as gigabytes of reclaimable-looking junk. Sized stat-only with `_bundle_size`/`_disk_bytes` (allocated blocks; a runtime asset holds a sparse `.dmg`), flagged from `STRANDED_ASSET_WARN_BYTES` = 1 GiB total. **This must never become a target** — SIP means a target here could only ever fail. Three degradation rules are load-bearing, all of them "unavailable ≠ absent": no simctl / a simctl error → `None` (unknown), a runtime list that parses but names **no builds** → also `None` (far likelier an unrecognised JSON shape than an empty registry, and believing it would report every asset on disk as stranded), an asset whose `Info.plist` cannot be read → counted as unreadable, never stranded. simctl runs on the caller thread and only the filesystem walk goes inside `_read_only_scan`, per the daemon/subprocess rule below. `_simctl_runtime_entries()` is the shared normaliser for simctl's three runtime-list shapes (also used by `scan_simulator_targets`).
- `run_tui_clean(targets)` — curses checklist; falls back to y/N prompts when non-interactive
- `translate_legacy(argv)` — v1 flag → v2 subcommand shim, runs before argparse
- `report.log` (sibling to `cleaner.py`, falling back to `~/Library/Application Support/MacCleaner/` when that directory isn't writable, or when it's inside a `.app` bundle regardless of writability — e.g. the app's bundled fallback engine running from inside its signed `.app`) stores the last 50 runs as JSON
- `snapshots.log` (same location rule as `report.log`; env override `MACCLEANER_SNAPSHOTS`) — every `scan` and real `clean`/`projects --clean` run (not `--dry-run`) appends a disk-usage snapshot, capped at the last 365 entries; a snapshot on the same calendar day as the previous one replaces it instead of appending, so 365 entries covers roughly a year. `report` prints a disk trend and `report --json` gains a `disk_history` key
- `alerts.json` (same location rule as `report.log`; env override `MACCLEANER_ALERTS`) — `disk-check`'s low-disk throttle state (last-notified timestamp), so a warning fires on the above→below transition and at most once per 24h after that
- Both `report.log` and `snapshots.log` writes are atomic (dump to a temp file, then `os.replace()`) so two concurrent runs (e.g. a launchd `clean --yes` overlapping a menu bar app scan) can't corrupt either file

### Safe vs. Review distinction
Each target has a `safe` bool. `--yes` / `auto_approve` only cleans `safe=True` targets. Review targets (`safe=False` — Xcode Archives, AI models, iOS backups, Trash, …) need explicit selection (`--targets id --yes` counts as consent) or interactive confirmation.

### Config
`config.json` (sibling to `cleaner.py`; installed: `~/mac-cleaner/config.json`) — missing keys merge with `DEFAULT_CONFIG` at load. Keys: `enabled_categories`, `skip_paths`, `log_threshold_mb`, `auto_approve`, `delete_mode` (`"rm"` | `"trash"`), `project_roots`, `project_min_age_days`, `project_git_check` (default `true`; disables the git dirty/unpushed check in `projects` when set `false`), `tmp_min_age_days` (default `1` since 2.15.0, was `3`; new in 2.5.0 — `/private/tmp` dirs younger than this are never offered by the `tmp` scanner; every tmp target is review-only, so the gate only shields an active task's workspace), `simulator_stale_days` (default `30`; new in 2.5.0 — a simulator not booted/used in this many days counts as stale), `app_leftover_min_age_days` (default `7`; new in 2.7.0 — orphaned app data under `~/Library` younger than this is never offered by the `leftovers` scanner, so an app removed a minute ago doesn't show up as an immediate false alarm), `notifications` (default `true`; gates `clean --notify` and app notifications), `low_disk_alerts` (default `true`; gates `disk-check`'s warning — independent of `notifications`), `low_disk_threshold_gb` (default `10`), `full_refresh_hours` (default `6`; app-side only, the engine never reads it — how often the app runs a full `scan` between its 60s `report` ticks), `show_in_dock` (default `false`; app-side only — the bundle is `LSUIElement` so it always *launches* menu-bar-only, and `CleanerBridge.applyDockVisibility()` promotes it to `.regular` at runtime when this is on, which is why `CleanerBridge.init()` loads settings rather than waiting on a view's `.task`). The cleanup cadence itself is `schedule`-subcommand state (launchd plists), not a config key — see below. `load_config()` also stamps a `known_categories` key on every load (not in `DEFAULT_CONFIG`, so `config set` rejects it) — it's how a category added in a new release (e.g. `tmp`/`simulators`/`leftovers`) gets auto-enabled for existing installs instead of silently staying off.

## V3 Swift kit (read-only, stages 1–2)

`swift/MacCleanerKit/` is the beginning of the V3 native engine (`docs/V3-SWIFT-ENGINE.md`), deliberately **read-only** — it has no deletion API and must not grow one before Stage 4's guard-first port. Three moving parts, each with its own tripwire:
- `tools/gen_contract_fixtures.py` → `tests/fixtures/*.json` — golden JSON contract fixtures generated from the real engine against a deterministic sandbox (stub `PATH` holding only `du`; 4 KiB-aligned seed files so APFS block rounding is identity; sandboxed scanner roots; `doctor` excluded as inherently machine-dependent). `TestContractFixtures` regenerates and diffs every run — an engine change that moves the contract fails the suite until fixtures are consciously regenerated.
- `tools/gen_swift_target_table.py` → `swift/.../TargetTable.generated.swift` — the Swift target table is **generated from `get_targets()`**, never hand-edited (same reasoning as `completions/complete_data.py`). `TestSwiftTableGenerated` pins freshness. Adding a target now means: regenerate completions data AND this file.
- `tools/check_swift_parity.py` — CI builds the kit (`swift build -c release --package-path swift/MacCleanerKit`) and runs this on every push: full 94-entry table equality plus per-target `(category, label, safe, exists, size_bytes)` scan parity in the fixture sandbox; cmd targets now receive the same comparison, with strict stub tools covering all four estimate parsers and simulator precomputed sizes. Only generated `estimateCommand` strings may run; `Target.cmd` remains descriptive and must never be executed by the read-only kit. Estimate processes use an isolated process group and file-backed output so the 15-second bound also handles shell pipelines holding stdout open. Parity is semantic, not byte-for-byte. `swift/MacCleanerKit/.build/` is gitignored.

## Install Path vs. Source
Source lives in this repo; installed copy lives at `~/mac-cleaner/`, app at `~/Applications/MacCleaner.app`. When testing changes, either re-run `install.sh` or call `cleaner.py` directly from the repo path (for the app, set `MACCLEANER_ENGINE` to the repo's `cleaner.py`).

## Distribution

### Shell completions
`completions/_maccleaner` (zsh) and `completions/maccleaner.bash` (bash) are hand-written, no runtime dependency — they complete subcommands, per-subcommand flags, `config` keys, and live category/target IDs by shelling out to `cleaner.py categories --json` (cached on disk, bounded by a wall-clock timeout, falling back to a static ID list if the engine can't be reached in time). `completions/` also holds a dev-only test harness (`run_tests.sh` and friends) that is deliberately **not** shipped — only the two completion files are copied by `install.sh` (to `~/mac-cleaner/completions/`, wired into `~/.zshrc` always and into `~/.bash_profile`/`~/.bashrc` only if those files already exist, each under its own rc guard string distinct from the alias guard) and packaged into the release CLI tarball. The drift tripwire is `TestCompletions` in `tests/test_cleaner.py`: it cross-references `build_parser()` against both completion files, so adding a subcommand or flag without updating them fails the suite. **That tripwire is necessary but not sufficient**: the CI-only behaviour harness `completions/run_tests.sh` additionally hardcodes whole expected flag lists per subcommand (e.g. `alias mreport flags` = the exact `-n --limit --stats --json --help` string) and the config action list — adding a flag passes `TestCompletions` locally and then fails only in CI's completion suite. When a parser surface changes, grep `run_tests.sh` for the affected subcommand and update its literal expectations too (2.15.0 learned this the CI-red way).

`completions/complete_data.py` (`CATS`/`TGTS`) is a committed **snapshot** of the live engine's category and target lists, consumed by `fake_engine.py` so the harness's tier-2/3 assertions run against a fixed list instead of whatever happens to be installed. It has no generator script, so adding a target means regenerating it — otherwise the real-engine tier-4 assertions move while the stub-backed ones stay put, and the counts in `run_tests.sh` disagree with each other. Regenerate with (from the repo root, `logs` filtered for the usual machine-dependence reason). Note it reads `DEFAULT_CONFIG`, **not** `load_config()` — the latter applies the local machine's `skip_paths`, which would silently omit whatever that developer happens to have excluded and bake the omission into the committed snapshot:
```bash
python3 -c "import json, cleaner; cfg=json.loads(json.dumps(cleaner.DEFAULT_CONFIG)); cats=[(c, cleaner.CATEGORY_DESCRIPTIONS[c]) for c in cleaner.ALL_CATEGORIES]; tgts=[(t['id'], t['label']) for t in cleaner.get_targets(cfg, all_categories=True) if t['category']!='logs']; open('completions/complete_data.py','w').write('CATS = %r\nTGTS = %r\n' % (cats, tgts))"
```
Then bump the hardcoded target counts in `run_tests.sh` (the `--targets` 1st/2nd/3rd-value assertions, the zsh alias-parity trio, and the tier-4 `ge` static floor) to match, and diff the regenerated file to confirm the change was purely additive — a regeneration run against a machine missing a tool must never silently *drop* an id.

### Release-time signing
`app/build.sh` always ad-hoc signs, for local/dev builds and as the fallback CI uses when nothing else is configured. `.github/workflows/release.yml` additionally probes for `MACOS_CERTIFICATE_P12` on every tag push; when it (and four other secrets: `MACOS_CERTIFICATE_PWD`, `APPLE_ID`, `APPLE_TEAM_ID`, `NOTARY_PASSWORD`) are present, it re-signs with a Developer ID certificate, notarizes (`notarytool submit --timeout 30m --wait`, fetching `notarytool log` on rejection), staples the ticket, and verifies with `spctl` before the release ships. Without the secrets, the release ships the same ad-hoc signed build as always, including the existing Gatekeeper caveat in the release notes. `docs/RELEASING.md` is the authoritative reference for the exact secrets, steps, and failure modes — read it before touching `release.yml`'s signing stage.

### Sparkle (auto-updates, v2.6.0+)
`app/build.sh` embeds `Sparkle.framework` via a cache-first, checksum-verified fetch (pinned SHA-256 for the exact upstream `.tar.xz`, plus a `.verified-sha256` marker beside the cache dir so a cache *hit* re-verifies too, not just a fresh fetch). The fetch is fatal under CI (`[ -n "${CI:-}" ]`) but falls back to `-DSPARKLE_DISABLED` for a local/offline dev build. `release.yml` signs the embedded framework inside-out (XPC services → `Autoupdate`/`Updater.app` → the framework itself → the outer app, strictly bottom-up, no `--deep`) before generating and uploading a signed `appcast.xml` — gated on **both** Developer ID signing **and** a sixth secret, `SPARKLE_ED_PRIVATE_KEY`. A build/release missing either one ships with no updater or no appcast entry, silently unless you check for it — see `docs/RELEASING.md` §7 (appcast mechanics, the key-correspondence gate, the one-unsigned-release-404s-the-feed hazard, and why key rotation is a two-release process, not a one-shot swap). `install.sh` prefers a freshly built Sparkle-bearing bundle over the committed one, but falls back to the committed bundle (or warns loudly) if a build somehow lacks `Sparkle.framework` — see `install.sh`'s step 7b. Sparkle updates the app bundle only, never the installed CLI engine at `~/mac-cleaner/cleaner.py`; `doctor` flags a version mismatch between the two and points at re-running `install.sh`.

### Homebrew cask
`Casks/maccleaner.rb` is written and validated (`brew style --cask` / `brew audit --cask` clean against a scratch tap). The tap (`Fullex26/homebrew-tap`) is **published and live** — `brew install --cask Fullex26/tap/maccleaner` (fully-qualified form only; the two-step `brew tap` + `brew install` fails on tap trust under Homebrew 6). The cask deliberately does **not** set `auto_updates true` yet even though v2.6.0 wires up Sparkle: the version the cask currently points at predates Sparkle, so setting it would strand every existing cask install with neither `brew upgrade` nor a self-update ever moving them forward. Add `auto_updates true` starting with the cask bump *after* the one that first points at a Sparkle-bearing build — see `docs/RELEASING.md` §5 for the exact sequencing.

## Optional Dependency
`rich` is optional — detected at import, falls back to plain text (`RICH = False`). All output paths have both rich and plain variants.

Persistent state updates require `_state_transaction(path)` around the entire read/modify/write, not just `_atomic_write_json`. Stable sibling `.lock` files must never be unlinked: replacing the lock inode lets two processes hold different locks for the same state. Lock waits are bounded; alert checks that cannot acquire the lock warn and do not claim notification delivery.
`projects --targets` must distinguish absence (`None`) from an explicitly empty string. The latter selects nothing in both cleanup and dry-run paths; never use truthiness to decide whether to apply the selection filter.

Project discovery runs in a daemon with a 120-second deadline, including root validation. A stop event and result lock freeze candidates before sizing/git checks; a resumed filesystem operation must not publish more candidates after the timeout. The daemon only discovers paths and never deletes or writes state.

Project artifact IDs must be unique across the discovered hit set. Every colliding slug gets a SHA-256 digest of its relative path; never assign suffixes by scan order or size, which could redirect a later explicit cleanup. The unsuffixed ambiguous ID is deliberately unknown, not an alias for the colliding group.
Project exclusions retain both lexical and resolved paths inside the bounded discovery worker, so an excluded symlink entry is protected as well as its destination. Skip directories under configured prefixes, and omit an entire artifact if it contains an excluded descendant: deleting the parent would otherwise bypass the exclusion. Resolve root aliases before comparing exclusions; omission applies equally to scanning, dry-run, and cleanup.
Swift read-only subprocess probes use `ReadOnlyProcess` for process-group deadlines and file-backed stdout. Pass literal argument arrays; only generated estimate commands use `/bin/sh -c`. Match Python timeouts (process list 10s, parent lookup 5s, simctl 60s, Spotlight 5s). `tools/check_swift_process_deadlines.py` has an external backstop so an unbounded helper fails CI instead of hanging it.

Configuration setting/category commands must lock `CONFIG_PATH.resolve()`, reload inside that lock, then mutate and save. Locking only the atomic write still loses other callers’ changes; locking the resolved destination keeps synced-config aliases on one transaction lock.
Minimum-free dry runs share safe-only candidate filtering with execution, including explicit selections. Their candidate list is an upper bound, not a predicted stopping point: trash, command targets, overlaps, and filesystem allocation prevent predicting free-space changes. `target_met` and `free_bytes` describe the initial reading; ordinary dry-run behavior stays unchanged.

Storage map loose-file rows must use `_disk_bytes(stat)` just like storage insights; `st_size` makes a 1 GiB sparse file appear under a zero-byte `du` parent. Keep minimum-size filtering on the same allocated-byte figure. `TestStorageMapAllocatedBytes` pins both behaviors with actual sparse temporary files.
For `disk-check --no-post`, authorizing app delivery requires a successful throttle-state save. A failed save must return `should_notify: false`, as a failed transaction lock does. Never rewrite `notified: true` to false after the CLI already posted a banner, even if the subsequent state save failed.

Configuration transactions must lock the local binding before resolving its destination, then lock canonical shared destinations. Sync-on/off and setting/category writers all use `_config_transaction`; destination-only locking cannot protect a symlink being replaced while a writer waits. Status remains read-only. Three real-process tests pin both sync-off orderings and sync-on during a delayed preference write. This serializes local processes, not external iCloud conflict resolution.

Storage map `incomplete: true` is an unavailable measurement, not an empty folder. The app must decode the optional flag, qualify the total, and retain partial rows with a warning. Missing/false flags mean complete, and accepting a complete refresh clears the previous warning. The app probe exercises the same acceptance method as the async bridge.
Bundle sizing deduplicates `(st_dev, st_ino)` within each traversal while summing allocated blocks. Keep the identity set local to the bundle: separate bundles must retain their own totals even when they share hard links. The walk stays stat-only and never follows symlinks.

Swift `ReadOnlyProcess` must terminate its process group on every exit path, not only on timeout. A shell can exit successfully while a background child survives. The standalone process probe checks both success and allowed nonzero exit with an external backstop and cleanup of its fixture groups.
Python read-only estimates use a dedicated process group and file-backed stdout. Always terminate the group and reap its shell, including successful shell exit: a descendant may retain pipes or keep running after its parent exits. Keep the 15-second deadline and zero-on-failure behavior; this helper is not the cleanup command runner.

Storage navigation requests can overlap across async suspension. Only the current request UUID may publish a map, publish an error, or clear the busy flag. `tools/check_storage_request_order.py` exercises the real bridge with controlled engine completions, including stale success/failure and a latest request that is still pending.
Storage-map completeness includes the du measurement, not only directory enumeration. A timeout, nonzero du exit, or missing root-total row must mark the result incomplete; preserve usable partial rows and propagate nested failures to the parent. A valid zero root row is complete. Keep the mount boundary flag and the private two-value sizing return compatible.

Legacy category-only arguments imply `scan`, including `--category=value`. Keep this fallback after explicit legacy modes (`--clean`, `--preview`, `--report`, config) so it cannot turn a requested command into a scan; argparse still validates the forwarded values.

Config sync must retain the active local binding until a complete replacement is ready. Sync-off atomically replaces the symlink without unlinking first; sync-on stages a symlink and atomically replaces the local binding, copying rather than moving settings into a new cloud file. Failed writes, link creation, or replacement must not silently reset `delete_mode` to its default.
Cleanup notification success counts include only `deleted` and `trashed`, never every non-skipped status. Share `CleanResult.notificationBody` between selected and automatic cleanup, append failures/skips separately, and retain the engine’s freed-byte title because a failed item can partially reclaim space. The real-bridge capture probe must never post actual notifications.

Resolve SwiftPM executables with `swift build --show-bin-path` using the same configuration/architectures as the successful build. The current macOS toolchain uses `.build/out/Products/Release`, so a hardcoded `.build/apple/Products/Release` path can silently omit a successfully built soak engine.

Only query/copy a Swift build output after that build succeeds. A failed compiler can leave an old executable at the expected path; existence alone does not prove it belongs to the current sources. Optional soak-engine failure must omit it and let app packaging continue.

- **Removal accounting:** `_remove` must propagate filesystem errors. `delete_target` credits a path only after its remove/trash succeeds; empty-only targets measure the parent before and after, including on failure, so hard links across siblings are deduplicated. A failed whole-directory removal can be partial, but its unknown reclaim is conservatively reported as zero, never its original size.

Path exclusions protect both named symlink entries and destinations (including resolved ancestors). Withhold a whole parent cleanup candidate when it contains an excluded descendant, even for empty-only sweeps. Do not let broad cache targets bypass narrower exclusions; Python and Swift must agree on filtered target presence as well as size.

Project artifact IDs must be unique across the discovered hit set. Every lossy identity gets a SHA-256 digest independent of the other candidates; never assign suffixes by scan order or size, which could redirect a later explicit cleanup. The unsuffixed ambiguous ID is deliberately unknown, not an alias for the colliding group.

Lossy dynamic IDs use `--` before the full identity digest: slugify collapses dash runs, so a literal slug cannot steal a generated ID. Never use encounter-order numeric suffixes for cleanup IDs; removing a candidate must not redirect an old ID to a different path. Hashing only currently colliding groups is insufficient: one singleton can replace another between scan and clean. Tmp identities are relative to the configured tmp root; log identities are names within Library/Logs; project identities are home-relative paths; leftovers use bundle IDs. Python/Swift parity includes real tmp and leftover collisions.

### Remaining read-only walk deadlines

`_read_only_scan` bounds filesystem discovery, including blocked directory reads, using a daemon worker whose result stays private until completion. Tmp, app inventory, leftovers, logs, and System temp enumeration use 120 seconds; each Storage map root/child enumeration uses 600 seconds. Subprocess probes and sizing must stay on the caller thread with their existing timeouts: abandoning a daemon supervising `subprocess.run` can orphan its child when the CLI exits. Nested map levels also run on the caller. Timeout returns an unavailable result and a stderr warning. Installed-app inventory returns `None` on timeout: leftovers must treat that as unknown and offer nothing, never as an empty set proving all apps absent. These workers must remain read-only and must not start subprocesses.

The same read-only deadline also covers `_target_paths` glob expansion and `_cleanup_children` pre-enumeration. Timeout is distinct from an empty directory: cleanup returns an error before accounting or mutation, scans expose `measurement_error`, and previews offer no unresolved paths. Never put `_remove`, Trash moves, or recursive deletion inside an abandoned daemon.

Doctor’s Homebrew cask ownership lookup also runs inside the read-only discovery deadline: globbing version directories or resolving a bundle link may stall. Timeout means unknown ownership (`None`), never a reason to remove or rewrite an installation.

Empty-only targets must refuse a symlink leaf before enumerating children. `_safe_to_delete` deliberately permits an in-home symlink leaf because unlinking it is safe, but `iterdir()` follows it; a `Library/Caches -> ~` link can otherwise offer personal files for removal. Refuse without removing the link, and mirror that behavior in dry-run. `TestEmptyOnlySymlinks` covers both general caches and Trash in both deletion modes.

Command cleanup owns a separate process group. On timeout or interruption, terminate that group and reap its shell before returning the error; killing the shell alone allows cleanup descendants to keep modifying storage after the caller reports failure. A separate session does not receive the caller’s Ctrl-C, so exceptional waits must clean up even for `KeyboardInterrupt`. The timeout remains 600 seconds and normal exit-code handling is unchanged. `TestCleanupProcessGroups` uses only a delayed temporary marker write.

App engine timeout must send TERM and allow one second for cleanup to unwind before guarded SIGKILL. Command cleanup temporarily handles TERM on the main thread by raising `SystemExit(143)`, so the owned-group exception path runs; restore the previous handler even when launching fails. Never return to immediate TERM/KILL. The real-bridge probe also pins the hard-stop bound for a TERM-ignoring engine.

Cleanup must defer launch-time SIGINT/SIGTERM until Popen has returned and the child handle is inside the group-cleanup try block. Raising from a handler during Popen can strand the newly created group; do not block signals with a mask that children inherit. Restore prior handlers on every exit.

ScanTarget.measurement_error means unavailable, not absent or empty. Dashboard visibility includes these rows regardless of exists/size; bulk/default selection and confirmation use canSelectForCleanup. Keep the optional field for older engines, and retain the last report if retry fails. The real-bridge scan measurement probe covers failed and successful retries; the layout probe includes many unavailable rows with long diagnostics.

Dashboard cleanup previews freeze target IDs and deletion mode, never executable paths. Reject incomplete previews, missing/duplicate IDs, unexpected statuses, stderr diagnostics, or mode changes before confirmation; actual cleanup still resolves the IDs through current engine guards. Command cleanup is not recoverable through Trash even when path cleanup uses Trash. Optional `preview_error` preserves partial resolved paths without claiming a complete preview.

History outcome summaries count known statuses explicitly; unknown statuses never count as success. Keep reported per-item and run bytes even for partial failures. Legacy missing or malformed items remain decodable with totals intact and display “Item details unavailable”; repeated IDs must not hide recorded outcomes.
