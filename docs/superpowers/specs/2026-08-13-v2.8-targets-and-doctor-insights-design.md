# MacCleaner v2.8 — New Safe Targets + Doctor Insights

**Date:** 2026-08-13
**Status:** Approved (design validated in-session with Jordan)
**Prior art:** `docs/superpowers/specs/2026-08-12-v2.7-app-uninstaller-design.md` (the immediately prior release); `CLAUDE.md`/`AGENTS.md` (engine conventions)

## Motivation

Jordan ran a real-machine storage audit outside this tool and asked that its
findings be "baked in." Triaging the audit's line items against MacCleaner's
existing coverage (see the session's own investigation) split them into four
buckets:

1. **Already covered** by an existing category (`/private/tmp`, simulators,
   Docker, Homebrew, Xcode DerivedData, generic app caches) — no work needed.
2. **Genuinely new, low-risk, regenerable** — XcodeBuildMCP workspace scratch
   data and Chrome's on-device optimization/prediction model cache. Neither
   has a target today; both are real gaps.
3. **Informational only** — swap pressure and files a process (typically
   `diskimages-helper`) is still holding open after they were deleted. There
   is nothing to *delete* for either (swap is OS-managed; a held-open file's
   space frees itself when the holding process exits) — the right fit is a
   `doctor` check, not a cleanup target.
4. **Explicitly out of scope**, matching the reasoning already used to scope
   v2.7's App Uninstaller: Codex/Claude session data (personal conversation
   history, not a cache), worktree pruning (needs the same git-safety
   checks as `projects`, but for a much higher-stakes deletion), and
   personal media (Civ VI archive, Health exports, drone footage — this is
   exactly the still-deferred read-only Storage Insights sub-project, not
   an auto-delete candidate).

This spec covers bucket 2 (new targets) and bucket 3 (doctor insights).
Buckets 1 and 4 require no code changes and are noted here only so the
record shows they were considered, not missed.

One existing-target correction surfaced during investigation: the audit's
"iOS DeviceSupport: 5.7 GiB" line item is **already covered** by the
existing `xcode-ios-device-support` target (`safe: True`, wholesale-deletes
the folder). Jordan confirmed leaving it as-is — selective-by-connected-
device logic was considered and explicitly declined as unnecessary
complexity for a marginal benefit (worst case is a one-time symbol
re-extraction on next device connect, not data loss).

## 1. New safe targets

Both added via the existing `add()` helper in `get_targets()`, `safe=True`,
no new categories, no new config keys.

- **`xcodebuildmcp-workspaces`** — category `xcode`, path
  `~/Library/Developer/XcodeBuildMCP` (real path confirmed on Jordan's
  machine; 1.0 GB there today). Description: "Build/workspace scratch data
  written by the XcodeBuildMCP tool; regenerated on next build."
- **`chrome-optimization-model-store`** — category `caches` (matching where
  the existing `chrome-cache` target already lives — Chrome's targets are
  grouped under `caches` in this codebase, not `browsers`; this spec follows
  that existing precedent rather than "fixing" it). Path:
  `~/Library/Application Support/Google/Chrome/optimization_guide_model_store`
  (~103 MB on Jordan's machine; unbounded growth over time as Chrome
  downloads more on-device models). Description: "Chrome's on-device
  ML prediction/optimization models; re-downloaded as needed."
- **`chrome-optimization-hint-cache`** — category `caches`, using `glob`
  (`~/Library/Application Support/Google/Chrome/*/optimization_guide_hint_cache_store`)
  since it's per-profile (`Default`, `Profile 1`, `Profile 3`, ...) — the
  same glob-for-variable-profile-name pattern the existing Firefox target
  already uses (`~/Library/Caches/Firefox/Profiles/*/cache2`). Description:
  "Chrome's per-profile page-optimization hint cache; regenerated as
  needed."

Deliberately **not** separately targeting `OptimizationHints` /
`OptimizationGuideModelsManifest` (Chrome's other two optimization-guide
directories) — both are under 1 MB combined on Jordan's machine, not worth
the added maintenance surface for negligible size.

## 2. Two new `doctor` checks

Added using the exact existing `check(name, status, ok=True)` pattern
already in `run_doctor()` — informational only, no delete action, no new
config keys, both best-effort and never fatal to `doctor` as a whole.

- **Swap** — parses `sysctl vm.swapusage`, computes percent used.
  - `ok=False` with actionable text above **75%** used, e.g. "swap usage
    high (95%) — consider closing memory-heavy apps or restarting."
  - Below 75%: a normal `ok=True` line, same style as the existing `Disk`
    check (which always reports free/total/percent regardless of level).
  - If `sysctl` is unavailable or its output doesn't parse, report "could
    not determine swap usage" rather than raising or failing the whole
    `doctor` run.
- **Held-open deleted files** — parses `lsof` output for deleted-but-
  still-open regular files, sums their sizes across all processes.
  - `ok=False` above **500 MB** total. `lsof`'s command-name field (`-c`
    equivalent) is always present per open-file record, so the status text
    always names the responsible process(es), e.g. "diskimages-helper is
    holding 612 MB of deleted files open — quit it or wait for it to exit
    to reclaim the space." When multiple processes each hold deleted files
    above a small per-process floor (10 MB, to keep the message from
    listing incidental noise), list up to 3 by name with the rest folded
    into "+N more processes."
  - At or below 500 MB: omit the check entirely (unlike Swap, this one has
    no "normal" informational value below its threshold — zero or a few MB
    of held-open deleted files is unremarkable on any Mac and would just be
    noise every single `doctor` run).
  - If `lsof` is unavailable or parsing fails, omit the check (same
    fail-open direction as above — never raise, never mark `doctor` itself
    unhealthy because of a signal that couldn't be read).

Both checks are read-only observations only. Neither offers, nor could
offer, a cleanup action: swap is entirely OS-managed, and a held-open
deleted file's space is reclaimed automatically the moment its holding
process exits — there is nothing this tool could safely do beyond
reporting the numbers.

## 3. Contract

`doctor --json`'s `checks` array gains up to two more entries (Swap always
present when readable, Held-open deleted files only when it fires) —
**purely additive**, no existing key removed or renamed. `doctor` (plain
text) output shows the same two lines using the existing check
presentation, no new formatting logic.

## 4. Testing

- **New targets**: verified the same way every other static target is
  tested today (`get_targets()`'s output for the right `id`/`category`/
  `safe`/`path`/`glob` fields) — no new test infrastructure needed, this
  is the existing `TestGetTargets`-style pattern.
- **Doctor checks**: two small, standalone parser functions —
  `_swap_usage_percent()` (parses `sysctl vm.swapusage` output) and
  `_held_open_deleted_bytes()` (parses `lsof` output) — so `subprocess.run`
  can be mocked in tests exactly like the existing Docker-estimate-parsing
  tests (`TestDockerEstimateParsing`, v2.6.1) already mock command output.
  Each parser gets a below-threshold and an above-threshold test case, plus
  an unparseable/unavailable-command case asserting graceful degradation
  (no exception, no `doctor`-run failure).
- **Contract**: a `doctor --json` test confirming the `checks` array still
  parses as valid JSON with the new entries present/absent per the
  threshold rules above, and that no existing key was removed or renamed.

## Non-goals (explicit)

- No new config keys (thresholds are hardcoded constants for v1 — Jordan
  considered and declined making them configurable, matching how most of
  `doctor`'s other checks are fixed-logic today).
- No app/Swift changes. `doctor` is a CLI-only diagnostic today (the app
  never calls it); this spec keeps it that way. Surfacing these checks in
  the app was considered and explicitly declined as unnecessary new
  surface area for two fairly niche, occasional-interest checks.
- No selective/smart iOS DeviceSupport logic (see Motivation) — explicitly
  declined.
- No action taken on either doctor check's findings — report only.
