# Engine v2.1 — Smarter Core + More Coverage

**Date:** 2026-07-23
**Status:** Approved
**Scope:** `cleaner.py` + tests + docs only. No SwiftUI app changes (sub-project 2), no distribution work (sub-project 3). All JSON changes are additive — the installed app keeps decoding under the superset rule.

This is sub-project 1 of the v2.1 release program (Engine → Native experience → Distribution).

---

## Goals

1. **More coverage** — 17 new cleanup targets, 3 new categories (17 → 20).
2. **Disk snapshots** — record free space + reclaimable on every scan/clean; surface trends in `report`.
3. **Git-aware `projects`** — dirty/unpushed projects are demoted to review, never swept by `--yes`.
4. **`clean --dry-run`** — show exactly what would be deleted, delete nothing.

## Non-goals

- Notifications, launchd, app auto-refresh, dashboard charts (sub-project 2 — but the snapshot data written here is what they will read).
- Homebrew Cask, signing, completions, Sparkle (sub-project 3).
- Any breaking change to existing JSON keys, target IDs, or exit codes.

## 2. Disk snapshots + trends

**Recording.** Snapshots append to `snapshots.log`, sibling to `cleaner.py` (installed: `~/mac-cleaner/snapshots.log`). Env override `MACCLEANER_SNAPSHOTS` for tests, mirroring `MACCLEANER_LOG`. When a snapshot is recorded:

- `scan` — always; a scan filtered by `--category` or `--min-size` is a partial measurement and records `null` reclaimable/categories, same as partial cleans.
- `clean` **without** `--targets` — after deletion, with re-statted `disk_free_bytes` and `reclaimable_bytes`/`categories` recomputed from the measured targets that were *not* cleaned (everything was measured, so this is accurate).
- `clean --targets …` — partial measurement, so `reclaimable_bytes` and `categories` are `null`; disk fields still recorded (the free-space datapoint is real regardless).
- `--dry-run` — never records.

Trend math uses `disk_free_bytes` from every snapshot but only non-`null` values for reclaimable figures.

Snapshot record:

```json
{
  "ts": "2026-07-23T14:05:00",
  "disk_total_bytes": 994662584320,
  "disk_free_bytes": 123456789000,
  "reclaimable_bytes": 9876543210,
  "categories": {"xcode": 5120000000, "node": 2048000000}
}
```

**Retention.** Capped at 365 entries. At most one entry per calendar day: a new snapshot on the same day as the last one **replaces** it instead of appending, so 365 entries means roughly a year of history. (Sub-project 2's auto-refresh will scan every few minutes; daily dedupe means those frequent scans collapse to one entry per day instead of flooding the log — an hourly dedupe key would only buy ~15 days of history under that auto-refresh cadence, not the ~year the cap implies.)

**Surfacing.** `report` gains a "Disk trend" section: current free space vs. the snapshot nearest 7 days ago and nearest 30 days ago, with deltas. Omitted entirely when fewer than 2 snapshots exist. `report --json` gains an additive top-level key:

```json
"disk_history": {
  "current": {"total_bytes": ..., "free_bytes": ...},
  "snapshots": [ ...oldest→newest, full retained list... ]
}
```

Named `disk_history`, not `disk`, because `scan --json` already uses `disk` for a human-readable string — reusing the key with a different type across commands would make the agent contract ambiguous.

**Failure handling.** A corrupt/unparseable `snapshots.log` is truncated and restarted (warning to stderr); snapshot write failures warn on stderr and never fail the command.

## 3. Git-aware `projects`

**Checks.** For each project hit, run in the same thread pool as size measurement, each with a 2 s timeout:

- repo? — `git -C <project_dir> rev-parse --is-inside-work-tree`
- dirty — `git -C <project_dir> status --porcelain` non-empty (untracked included, ignored excluded — it's an *activity* signal, not a data-loss signal)
- unpushed — `git -C <project_dir> rev-list --count --branches --not --remotes` > 0. A repo with no remotes counts as unpushed (nothing is backed up anywhere), which is the conservative reading.

`git` missing, timing out, or erroring degrades to "no info" (treated as non-repo). Config key `project_git_check` (default `true`) disables the checks entirely.

**Behavior.** Dirty **or** unpushed ⇒ the project's generated target gets `safe=False` in `projects_to_targets()`: it still appears in listings with a `[dirty]` / `[unpushed]` badge, is never swept by `--yes`, and remains cleanable via explicit `--targets <id>` or interactive selection — the existing safe/review model, no new concepts.

**JSON.** Each project hit gains an additive `git` key: `null` for non-repos / no info, else `{"dirty": bool, "unpushed": bool}`.

## 4. `clean --dry-run`

Applies to `clean` and `projects --clean`. A dry run resolves **exactly** what a real run with the same flags would delete, then stops:

- Selection semantics identical to a real run: bare `clean --dry-run` previews what `--yes` would sweep (safe targets only); `--targets` previews those specific IDs; `--category` / `--min-size` filter as usual.
- Path targets: globs expanded to concrete paths, each with its measured size. `empty_only` targets list their top-level entries. Cmd targets print the command that would run (never executed).
- Nothing is deleted, nothing is written to `report.log` or `snapshots.log`. Exit 0.
- `--json`: the `clean` result shape plus `"dry_run": true` and a per-target `"paths": [{"path": ..., "size_bytes": ...}]` array (additive).
