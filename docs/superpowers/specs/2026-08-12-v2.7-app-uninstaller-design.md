# MacCleaner v2.7 — App Uninstaller (orphaned leftover-file cleanup)

**Date:** 2026-08-12
**Status:** Approved (design validated in-session with Jordan; trigger mechanism, detection precision, and location scope each confirmed explicitly)
**Prior art:** v2.1–v2.6 specs in this directory (`scan_tmp_artifacts()` is the direct structural template); `AGENTS.md` (machine contract); `CLAUDE.md` (engine conventions)

## Motivation

MacCleaner has always cleaned regenerable developer/cache junk, never a user's
actual software or data. Jordan asked how to expand coverage further —
"scan for even more, delete even more junk... Applications, Documents." The
honest answer: Applications and Documents are a different risk category
(irreplaceable data, not regenerable caches), so the existing safe/one-click
delete model can't extend there wholesale without eroding the trust it's
built on.

App Uninstaller is the piece of that idea that DOES fit the existing safety
model cleanly: when you delete an app yourself (via Finder), macOS leaves
its caches, preferences, and saved state behind forever — dead weight with
no owner. Finding and removing *that* is exactly the same shape of problem
the `tmp` scanner (v2.5) already solved for `/private/tmp` build litter:
dynamic discovery, review-only targets, precise (not fuzzy) matching.

## Non-goals

- **No live-app deletion.** MacCleaner never deletes an installed `.app` —
  only leftovers of apps *already* gone. This is a deliberate, explicit
  boundary: it introduces zero new "delete real software" capability.
- **No fuzzy/name-based matching.** Only bundle-ID-keyed locations are
  scanned. A location that isn't reliably bundle-ID-keyed is out of scope
  rather than guessed at (see §5).
- **No `~/Library/Application Support` matching in v1** — usually keyed by
  the app's display name, not its bundle ID, and once the app is gone there's
  no reliable way to recover that name without new persistent state (see
  §5's Future Direction note). Often the single biggest leftover location,
  but guessing at it is exactly the imprecision bundle-ID matching exists to
  avoid.
- **No Containers, Group Containers, or LaunchAgents in v1** — see §5.
- No new general "outside `$HOME`" capability — every location this scans is
  already strictly inside `$HOME`; no carve-out to the home-only rule is
  needed or added.

## 1. Detection: bundle-ID orphan matching

A new dynamic scanner, `scan_app_leftovers(config)`, structurally mirrors
`scan_tmp_artifacts()` (cleaner.py, v2.5):

- **Build the installed set:** enumerate top-level `.app` bundles in three
  root directories, reading each one's `CFBundleIdentifier` via `plistlib`
  (the same technique `doctor`'s existing `_app_bundle_version()` helper
  already uses for `Info.plist`). Bundle IDs are lowercased for comparison
  (some vendors are inconsistent about casing). Unreadable/malformed
  `Info.plist`s are skipped, never fatal to the scan. The three roots are
  configurable via **`MACCLEANER_INSTALLED_APPS_DIRS`** (colon-separated,
  PATH-style; default `/Applications:$HOME/Applications:/System/Applications`)
  — this is the sandboxing seam tests use, and it exists specifically to
  avoid the exact bug just fixed in `doctor`'s app check this session (a
  hardcoded system path with no test-isolation override silently depending
  on whatever happens to be installed on the machine running the suite).
- **Scan five bundle-ID-keyed leftover roots**, all located under one
  configurable library root, **`MACCLEANER_LEFTOVER_LIBRARY_ROOT`** (default
  `$HOME/Library`) — tests point this at a scratch directory containing
  fabricated `Caches`/`Preferences`/etc. subdirs, exactly mirroring
  `MACCLEANER_TMP_ROOT`'s pattern. The five subdirectories under that root:
  `Caches`, `Preferences`, `Saved Application State`, `HTTPStorages`,
  `WebKit`. Each root's top-level entries
  are matched against a reverse-DNS bundle-ID shape
  (`^[a-z0-9]+(\.[a-z0-9-]+)+$`, case-insensitive) — entries that don't look
  like a bundle ID are ignored outright (this also naturally skips Apple's
  own non-bundle-ID housekeeping files in these directories). Preferences
  entries are `<bundle-id>.plist` — the `.plist` suffix is stripped before
  matching.
- **Orphan test:** a matched bundle ID is a candidate only if it is NOT in
  the installed set.
- **Guards (all mandatory, mirroring the tmp scanner's guard list):**
  - Hard-exclude `com.apple.*` and MacCleaner's own bundle ID
    (`com.fullex.MacCleaner`) unconditionally — checked directly against the
    candidate ID, independent of and in addition to the installed-set check,
    so this can never regress even if the installed-app enumeration has a
    gap (e.g. an Apple app that lives outside the three scanned roots).
  - Min-age grace period: `app_leftover_min_age_days` (new config key,
    default `7`) — a candidate's mtime (across all its matched paths, using
    the newest) must be older than this, protecting against a false
    positive mid-reinstall (the app was deleted and is about to be put back)
    or a delayed Spotlight/mdfind index during a fresh install.
  - Never follows symlinks; only bundle-ID-shaped names are considered;
    plain files at these roots that aren't directories (where a directory is
    expected, e.g. Caches) are skipped, not misinterpreted.

## 2. One target per app

Each orphaned bundle ID becomes **one target** aggregating every leftover
root it has matching data in — not one target per location. This needs one
small, additive engine change:

`_target_paths(t)` (cleaner.py) gains a third branch:

```python
def _target_paths(t):
    if t.get("glob"):
        ...  # unchanged
    if t.get("paths"):
        return t["paths"]
    if t.get("path"):
        return [t["path"]]
    return []
```

`t["paths"]` is a plain list of concrete `Path` objects — no glob expansion,
no skip_paths re-filtering needed (the scanner already excludes nothing via
`skip_paths` today; if a future version wants that, it filters at
construction time exactly like `scan_tmp_artifacts` does for `tmp` targets).
This is a two-line, purely additive change: every existing target continues
using `path`/`glob` exactly as before, and no other code path is touched.

`app_to_targets(hits)` (mirroring `tmp_to_targets`) builds the target dicts:
id `leftover-<bundle-id-slug>` (via the existing `slugify()`), category
`leftovers`, `safe=False`, description listing which of the five locations
were found (e.g. "Caches, Preferences, Saved State — orphaned since app was
removed"), `paths` set to the matched directories/files for this bundle ID.

## 3. Category, config, and safety

- New category `leftovers` — added to `ALL_CATEGORIES`, picked up
  automatically by the existing `known_categories` migration (v2.5) so
  existing installs get it without any special-casing.
- `CATEGORY_DESCRIPTIONS["leftovers"]` — something like "Cache, preference,
  and saved-state files left behind by apps you've already deleted — review
  carefully."
- New config key: `app_leftover_min_age_days` (default `7`).
- `safe=False` always — review-only, identical consent model to every other
  dynamic scanner (`tmp-*`, `simulator-*`). A scheduled `clean --yes` can
  never touch these; explicit `--targets ... --yes` or interactive
  confirmation required.
- **No new carve-out to the home-only delete rule.** All five scanned roots
  are strictly inside `$HOME`; `_safe_to_delete`'s existing check already
  permits them. This is materially safer than the v2.5 tmp scanner from an
  engine-invariant standpoint — it doesn't touch the one deliberate
  exception at all.
- Scanner scoping (v2.6 `collect_targets` hints) applies here exactly like
  it does for `tmp`/`simulators`: a `--category leftovers`/`--targets
  leftover-*` selection runs the app-leftover enumeration; a scoped clean
  for an unrelated category skips it.

## 4. Surfacing (engine + app)

- `scan`, `clean`, `clean --dry-run` and their `--json` outputs gain
  `leftover-*` targets exactly like `tmp-*`/`simulator-*` do today —
  additive JSON, no contract changes.
- `categories` lists the `leftovers` category (empty targets array, per the
  existing tmp/simulators precedent) but never the per-app dynamic IDs —
  same reasoning as `projects`/`tmp`: dynamic IDs are unstable and must not
  leak into the completions' live-ID pipeline.
- **No new app view.** This folds into the existing Dashboard category list
  using the row idiom already shared by Docker/tmp/simulators — colored
  category dot (`categoryColor("leftovers")` + `categoryDisplayName`, both
  already extensible in `DesignSystem.swift`), monospaced size, REVIEW
  badge, bulk-select bar. Zero new Swift files.

## 5. Deliberate scope boundary (why, precisely)

| Location | Keyed by | v1 decision |
|---|---|---|
| Caches, Preferences, Saved App State, HTTPStorages, WebKit | Bundle ID (Apple convention) | **In scope** — precise match |
| Containers | Bundle ID (Apple convention) | **Out of v1** — often the single largest leftover for sandboxed apps, and still precisely bundle-ID-matched, but a materially bigger blast radius per target (can hold substantial persistent data); a reasonable v1.1 addition once the base scanner has field experience |
| Application Support | App display name (not bundle ID) | **Out of v1** — no reliable identifier survives app deletion; matching would mean guessing, which is exactly what bundle-ID matching was chosen to avoid |
| Group Containers | Team/group ID (not 1:1 with bundle ID) | **Out of v1** — same imprecision problem as Application Support |
| LaunchAgents | Bundle ID (usually) | **Out of v1** — a leftover agent *plist* is inert, but a helper daemon could theoretically still be loaded even after its parent app is gone; safely handling that needs `launchctl` interaction this spec deliberately doesn't take on |

**Future direction (not v1):** a persistent map of bundle-ID → display-name,
snapshotted while apps are still installed (e.g. during `scan`), would let a
later version match Application Support by name even after the app's gone.
Real new statefulness — out of scope here, noted so the boundary reads as a
decision, not an oversight.

## Testing

- **Detection tests:** installed-app enumeration (mock `Info.plist` fixtures
  incl. malformed/unreadable → skipped not fatal); orphan classification
  (present-in-installed-set → excluded, absent → candidate); the
  `com.apple.*`/self-exclusion guard tested independently of the
  installed-set check (a fixture where the exclusion is the *only* thing
  preventing a match); min-age gate; non-bundle-ID-shaped names ignored;
  symlinks never followed/matched. All via `MACCLEANER_LEFTOVER_LIBRARY_ROOT`
  and `MACCLEANER_INSTALLED_APPS_DIRS` (§1) so tests never touch the real
  `~/Library/*` or `/Applications`, mirroring `MACCLEANER_TMP_ROOT`.
- **`_target_paths` regression test:** the new `paths` branch returns the
  list verbatim; existing `path`/`glob` behavior unchanged (regression
  guard).
- **Carve-out non-event test:** explicitly assert `_safe_to_delete` (not the
  tmp-only carve-out) is what permits leftover-target deletion — i.e. these
  targets carry no `tmp_scan`-style marker and don't need one.
- **Contract:** `categories --json` shows `leftovers` with zero targets
  (dynamic IDs never leak in); `scan --json`/`clean --dry-run --json` show
  real `leftover-*` ids; `clean --yes` (unscoped) never touches them.
- **App:** no Swift changes beyond the existing extensible `categoryColor`/
  `categoryDisplayName` maps gaining one more entry — verified same as any
  other category addition (build clean, both appearances).
