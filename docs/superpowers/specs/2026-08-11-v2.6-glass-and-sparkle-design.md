# MacCleaner v2.6 — "Glass & Sparkle": UI/UX overhaul + Sparkle auto-updates

**Date:** 2026-08-11
**Status:** Approved (design validated in-session with Jordan via the visual companion; direction, menu bar scope, and update behavior each confirmed explicitly)
**Prior art:** v2.0–v2.5 specs in this directory; `AGENTS.md` (machine contract); `docs/RELEASING.md` (release procedure)

## Motivation

The app is functionally complete but visually stock — plain inset lists, default
toggles, no identity beyond the icon. Jordan's ask: "a full UI/UX upgrade — it
should be super cool and beautiful feeling," plus the concrete gap from daily
use: no Select All on the Projects tab. Separately, v2.4 deferred the Sparkle
auto-updater "until a Developer ID exists" — one now exists and every release
notarizes automatically, so direct-download users can finally stop being
stranded on old versions. Both ship together as v2.6: the last version anyone
has to download by hand is the one that makes the app beautiful.

## Design direction (validated visually)

**"A's bones, C's blood"** — chosen from three mocked directions (Refined
Native / Health Dashboard / Pro Dark Glass), then confirmed as a hybrid
mockup in light + dark:

- **Structure from A (Refined Native):** sidebar navigation replacing the top
  tab bar, native controls, generous whitespace, quietly premium.
- **Data language from C (Pro Dark Glass):** monospaced digits for every size,
  per-category colored dots, one cyan accent, glass materials
  (`.ultraThinMaterial`), slim gradient progress bars.
- **Adaptive:** one layout, both appearances. Dark mode carries the full C
  mood (deep gradient backgrounds, glass panels, glowing accent); light mode
  stays refined native. System appearance drives it — no in-app theme toggle.

## 1. Design system

New `app/Sources/DesignSystem.swift` — the single home for the visual
language, so views never hardcode style:

- **Accent:** cyan (`Color.accentCyan`, roughly #22D3EE dark / #0E7490 light —
  exact values tuned in implementation against both appearances).
- **Category colors:** a stable mapping `categoryColor(_ name: String) -> Color`
  covering all 22 categories (hash-derived fallback for future ones), used for
  the dot in every target row and popover tile.
- **Typography:** `.monospacedDigit()` for all byte counts; size text style
  helpers (`heroNumber`, `rowLabel`, `metaCaption`).
- **Surfaces:** glass panel modifier (`.glassPanel()` →
  `.background(.ultraThinMaterial, in: RoundedRectangle...)` with a hairline
  border in dark), gradient bar style for disk usage.
- **Motion:** `.animation(.snappy, ...)` defaults; `contentTransition(.numericText())`
  for changing numbers; a `ProgressShimmer` used during cleans. Subtle only —
  no celebratory effects.

## 2. Window structure: sidebar

`MacCleanerApp`'s window swaps the top `TabView`/picker for a
`NavigationSplitView`: sidebar (Dashboard / Projects / History / Settings,
SF-symbol icons, accent-tinted selection) + detail. Minimum window size keeps
the current footprint. Keyboard: ⌘1–⌘4 switch sections.

## 3. Per-view overhaul

- **Dashboard:** header becomes hero number ("12.4 **GB reclaimable**") with
  meta line (free space · last scan time) and the slim gradient disk bar
  (replacing the stock `ProgressView`); the existing `DiskTrendView` chart
  restyles to match (accent line, glass card). Target list keeps grouped
  categories but each row gets the category dot, monospaced size, and the
  REVIEW badge restyled (outline amber). **New bulk-select bar** above the
  list: `All · None · Safe only` (Safe only reproduces the seeded default).
  Footer clean button becomes the accent pill; **cleaning shows live per-item
  progress** — the engine already emits per-item results at the end, so live
  progress is driven app-side: the item list with per-row spinners/checks as
  `CleanerBridge` streams what it's about to delete (implementation may show
  determinate progress across selected items as each `clean --targets` batch
  is one process — acceptable: animate through selected items optimistically,
  reconcile with the real per-item statuses from the JSON result; never show
  "done" before the process exits).
- **Projects:** **Select All / None** (the user-reported gap), same row
  language (kind dot by artifact type, monospaced sizes, age caption), same
  footer pill. Git badges (dirty/unpushed) restyle as outline chips.
- **History:** entries as glass cards (date, freed hero number, item count),
  restyled from the current plain list.
- **Settings:** grouped into glass sections (General / Schedule / Alerts /
  **Updates** — new); controls stay native. The Updates section hosts
  Sparkle's "Check for Updates…" button, "Automatically check" toggle
  (default on), and the current version string.
- **Menu bar popover:** `MenuBarExtra` switches to `.window` style — a compact
  glass panel: disk gauge ring (percent used), reclaimable hero number, top 3
  categories by size (dot + name + size), a one-click **Clean safe items**
  accent button with inline result ("Freed 2.1 GB ✓"), and footer links (Open
  MacCleaner · Quit). The panel is the flagship of the new design.
- **Removed/kept:** `LSUIElement` stays (no Dock icon); all existing
  functionality is preserved — this is a reskin + additions, no behavior
  removals. The `full_refresh_hours`/60s tick cadence is untouched.

## 4. Engine change (exactly one): scanner latency scoping

The deferred v2.5 item ships now because the popover's one-click clean pays
the scanners' cost (two simctl calls + du) for a safe-only clean that can
never include them. `collect_targets(config, all_categories=False,
categories=None, target_ids=None)` gains optional selection hints: when a
category set is provided and excludes `tmp`/`simulators`, the respective
scanner is skipped; when `target_ids` is provided, a scanner runs only if an
id with its prefix (`tmp-` / `simulator-`) is requested. `scan`/`clean`
handlers in `main()` pass what the CLI invocation knows. Unscoped calls
behave exactly as today. JSON contract unchanged; tests cover: scoped-out
category skips the scanner (mock assert not-called), scoped-in runs it,
unscoped unchanged, `clean --targets npm-cache --yes` never invokes simctl.
The other three deferred v2.5 items stay deferred.

## 5. Sparkle auto-updates

- **Behavior:** check + prompt. Daily automatic check
  (`SUEnableAutomaticChecks` default on, toggleable in Settings), Sparkle's
  standard update window with release notes (fed from the appcast item's
  description — the release body). Manual "Check for Updates…" in Settings.
- **Framework embedding (the no-Xcode constraint):** embed the **prebuilt
  Sparkle XCFramework** (latest Sparkle 2.x pinned by exact version) rather
  than converting the build to SPM. `app/build.sh` gains a fetch step:
  download the official Sparkle release archive to a cache dir
  (`build/sparkle-<version>/`), verify a pinned SHA-256, extract
  `Sparkle.framework` (macOS slice), copy into
  `Contents/Frameworks/Sparkle.framework`, link with
  `-F <path> -framework Sparkle -Xlinker -rpath -Xlinker @executable_path/../Frameworks`.
  Offline/no-network builds: if the cached framework is absent and the
  download fails, build.sh continues WITHOUT Sparkle (compile-time flag
  `-DSPARKLE_DISABLED` guards the integration code) and prints a warning —
  local dev never breaks because GitHub is unreachable. CI/release builds
  treat fetch failure as fatal.
- **App integration:** `UpdaterManager.swift` wrapping
  `SPUStandardUpdaterController` (started at app init when Sparkle is
  compiled in), exposed to Settings via an observable. `Info.plist` gains
  `SUPublicEDKey` (the EdDSA public key) and `SUFeedURL` =
  `https://github.com/Fullex26/MacCleaner/releases/latest/download/appcast.xml`.
- **Keys:** generate one EdDSA pair with Sparkle's `generate_keys` at setup
  time; public key → `Info.plist` (committed), private key → repo secret
  `SPARKLE_ED_PRIVATE_KEY` (same handling pattern as the signing certs; never
  committed, never printed).
- **Appcast:** `release.yml` generates `appcast.xml` per release — one
  `<item>` for the current version: title, version, the release body as
  description, enclosure URL of the universal zip, its length, and the
  `sparkle:edSignature` produced by Sparkle's `sign_update` with the secret
  key. Uploaded as a release asset; the stable
  `releases/latest/download/appcast.xml` URL means the newest release's
  appcast is always what installed apps poll. (Single-item appcasts are
  valid; Sparkle only needs to see a version newer than the running one.)
- **Signing/notarization order in release.yml:** sign
  `Contents/Frameworks/Sparkle.framework` (and its nested XPC services)
  inside-out with the Developer ID identity and hardened runtime BEFORE
  signing the app, then notarize as today. The unsigned-fallback path (no
  secrets) ships Sparkle ad-hoc signed like the rest of the bundle.
- **Coexistence with Homebrew:** cask users may update via either channel;
  no conflict (Sparkle replaces the .app in place; `brew upgrade` does the
  same). Cask gains no `auto_updates` stanza change in this release beyond
  `auto_updates true` (accurate once Sparkle ships, and stops brew from
  flagging version drift).
- **Proving it:** a local test appcast (file:// or localhost feed pointing at
  a bumped build) exercises the full update flow before release; the real
  end-to-end proof is the next release after v2.6.0 updating a v2.6.0
  install.

## Non-goals

- No in-app theme toggle (system appearance only)
- No new cleanup targets or JSON contract changes (beyond nothing — the
  contract is untouched; scanner scoping changes no output shapes)
- No SPM/Xcode-project migration; `swiftc` build stays
- No fully-automatic silent updates (explicitly rejected for check+prompt)
- The remaining three deferred v2.5 engine items stay deferred
